# Тесты

Команды ниже даны для активированного виртуального окружения. Если окружение не активировано, запускайте интерпретатор из него напрямую:

- Git Bash: `venv/Scripts/python.exe -m pytest` (слэши прямые: в Git Bash обратный слэш съедается, и `venv\Scripts\python.exe` не находится);
- PowerShell / cmd: `venv\Scripts\python.exe -m pytest`.

Просто `python -m pytest` без активации запускает системный Python, в котором pytest не установлен.

```bash
pip install -r requirements-dev.txt     # pytest и pytest-asyncio
pytest                                   # всё, кроме реальных моделей (около 45 с)
pytest tests/test_pipeline.py            # один файл
pytest -k "cache or hygiene"             # по имени
pytest --run-models                      # плюс тесты на реальных моделях (около 1,5 минуты)
```

Настройки в `pytest.ini`: асинхронные тесты идут в одном общем цикле событий (так же, как работает сервер), маркеры `db` и `models`.

## Что проверяется

| Файл | Что проверяет | Нужно |
|---|---|---|
| `test_pipeline.py` | маршрут запроса (болтовня, шлюз, защитник), нужная модель на каждой ступени, гигиена, точное слово (Ё/регистр/пробелы), кэш повторов и его ограниченность, сбои моделей, недоступные ступени, **асинхронность**: 10 запросов идут параллельно, цикл событий не блокируется ни моделью, ни BERT | ничего |
| `test_llamacpp_backend.py` | **запуск моделей**: процессы llama-server поднимаются и ждутся до готовности, слоты, очередь и 429-ситуация, падение модели при старте и во время работы, нет файла модели или `llama-server`, остановка и чистка забытых процессов, весь старт пайплайна | ничего (поддельный сервер) |
| `test_api.py` | HTTP API: регистрация, вход, выход, прогресс и фазы, `/predict`, **запись попыток в БД** (текст, ответ, трасса), победа и новое слово, уровни мира, лимиты и `Retry-After`, один запрос на игрока, параллельные игроки | PostgreSQL |
| `test_leakcheck.py` | проверка утечки слова: прямые и обходные формы, кодировки, ложные срабатывания, перевод для каждого слова призраков | ничего |
| `test_config_and_prompts.py` | согласованность настроек (ступени, модели, призраки), свойства промптов, разбор ответа шлюза, реплики отказа | ничего |
| `test_text_and_schemas.py` | очистка текста (NUL и управляющие символы), проверка запросов API | ничего |
| `test_classifiers_and_scripts.py` | заглушка BERT, понятные ошибки при отсутствии весов, локальная загрузка BERT, разбор файлов GGUF в `download_models.py` | ничего |
| `test_real_models.py` | реальный BERT и четыре модели без интернета: все запущены, BERT отличает болтовню от атаки, шлюз, защитник каждой ступени, параллельные запросы | `--run-models`, веса |

## Как устроены тесты с БД

Фикстура `db_schema` (`conftest.py`) создаёт временную схему `test_<случайное>` внутри базы из `DATABASE_URL`, создаёт в ней таблицы приложения и подключает к ней приложение отдельным движком (`search_path` указан только на эту схему). В конце схема удаляется, а специальная проверка падает, если в рабочей схеме `public` появились тестовые игроки. Ваши данные не затрагиваются. Нужны права на `CREATE SCHEMA` (есть у владельца базы); если подключиться нельзя, тесты с БД пропускаются с объяснением.

Языковые модели в тестах заменяет `RecordingBackend` (`helpers.py`): он запоминает вызовы и умеет задерживаться, отказывать и «не успевать» по очереди. Вместо `llama-server` в тестах бэкенда запускается `fake_llama_server.py` с тем же HTTP-интерфейсом.

Тексты, на которых заглушки ведут себя предсказуемо, лежат в `helpers.py` (`BENIGN`, `BARE_REQUEST`, `TECH_ATTACK`, `SOCIAL_ATTACK`).
